## Método y alcance del inventario

Se fijan IDs, runs, commits y SHA256 ZIP originales en `tools/apk/source-artifacts.json`. Se descargan desde Actions autenticados únicamente durante CI, se verifican digest y CRC, y se extraen todos los APK de esos diez ZIP. No se ejecuta Gradle ni se genera keystore. La credencial efímera no se escribe a archivos y se retira al redirigir la descarga a otro host.

Por cada APK, Android SDK Build Tools 36.0.0 ejecuta:
```sh
apksigner verify --verbose --print-certs archivo.apk
aapt dump badging archivo.apk
```
Se conservan stdout/stderr y exit code de ambos comandos. **Los 28 comandos (14×2) retornaron 0**. Firma v2 verificada en todos; v1/v3/v3.1/v4 false. No hay rotación de certificado v3 acreditada que permita reconciliar los fingerprints distintos. El DN idéntico `C=US, O=Android, CN=Android Debug` no significa certificado idéntico.

Inventario acotado a las entregas aceptadas con persistencia T03–T07A y sus dos plataformas cuando existen. No es un catálogo de todos los builds fallidos/temporales ni de APK instalados en equipos de usuarios. No se aportó el APK de una instalación real. El listado global de artefactos no está expuesto por el endpoint fetch del conector; se consultaron individualmente los siete runs aceptados y se obtuvieron diez artefactos no expirados.

## Instalación segura del APK de entrega

El APK seleccionado es el principal API36 de T07A, no el de instrumentación. T07B no genera una nueva app ni una clave de distribución. API24/API36 identifican el emulador usado para validar; ambos APK principales conservan minSdk 24.

### Usuario nuevo / paquete aún no instalado

1. Descargar el APK principal desde el artefacto de T07A y contrastar SHA256 con la tabla.
2. Comprobar la firma con `apksigner verify --verbose --print-certs actual.apk`.
3. Comprobar si existe instalación: `adb shell pm list packages com.aik1a.localcash`. Si aparece el paquete principal, detener este procedimiento y evaluar actualización.
4. Con el paquete principal ausente: `adb install actual.apk`. No instalar el APK `*.test` de instrumentación.
5. Configurar biometría compatible en Android antes de abrir contenido financiero. La app mantiene el gate; no hay PIN propio ni bypass.

### Instalación existente

No desinstalar, no ejecutar `pm clear`, no borrar SQLite ni aceptar una eliminación de datos para superar un error de firma. No usar `-d`, cambios de packageName ni APK vuelto a firmar.

Para diagnosticar sin tocar SQLite:
- Identificar el APK instalado mediante `adb shell pm path com.aik1a.localcash`; si el entorno permite leer el archivo de código, copiar únicamente ese APK con `adb pull <ruta-base.apk> instalado.apk`. Esto no extrae datos financieros.
- Ejecutar `apksigner verify --verbose --print-certs instalado.apk` y el mismo comando sobre el candidato; comparar fingerprints SHA256 completos, no el DN “Android Debug”.
- Leer package/version con `aapt dump badging`. La coincidencia de nombre/versión o la etiqueta debug no acredita firma compatible.
- Si el certificado difiere en estos APK sin rotación, **detener la actualización**. Conservar la app instalada y sus datos. No hay migración/exportación implementada ni autorización para crearla en T07B.
- Solo con misma firma, mismo package y versionCode no decreciente, se puede planificar `adb install -r candidato.apk`. Registrar primero los datos de prueba en un AVD descartable, el resultado completo y después comprobar datos/saldos/relaciones/reapertura. No presentar un ensayo sobre el mismo archivo como actualización histórica.
- Para una instalación real que no esté en el inventario, la compatibilidad queda **NO DETERMINADA** hasta contrastar su certificado. No asegurar conservación de datos basándose en esta matriz de otras instalaciones.

La estrategia de firma estable/recuperación de una clave histórica requiere decisión del Orquestador. No se generan ni se publican claves aquí. Si no se dispone del firmante autorizado de una instalación histórica, este trabajo no aporta una ruta de actualización con conservación de sus datos.
